절벽에서 굴러오는 슬라임을 테니스처럼 받아쳐 터뜨리는 세로형 모바일 캐주얼 액션입니다. 클라이언트 코드는 AI 코딩 에이전트와 함께 작성했습니다.

AI와 일하는 판부터 만들었습니다

  • 규칙 문서. 요구를 요약하고 확인받기, 코드는 보여 주고 승인 뒤 작성, 이미 있는 기능은 재사용, 삭제는 반드시 허락받기, 요청 밖 리팩토링 금지.
  • 맥락 문서. 게임 룰 14편(랠리, 공, 콤보·피버, 슬라임, 그리드 등), 아키텍처 결정 기록, 밸런스 데이터 사용법, 코딩 컨벤션을 AI가 매 작업마다 읽는 참고 문서로 연결했습니다.

  • 고르는 기준은 제가. 툴 UX는 "시각화 → 배우지 않고 쓰기 → 편집 편의 → 가독성" 순으로 정해 두고, AI 제안을 이 순서로 골랐습니다.

Slime Busterscase-01 · 구조화

> Q. 조작 방식이 계속 바뀌는데, 게임 코드는 그대로 둘 수 있을까?

입력을 클래스가 아니라 조립으로

기획 단계에서 조작안이 여러 번 바뀌고 늘어났습니다. 조작안마다 클래스를 두는 구조라, 버튼 배치 하나를 바꿔도 아바타 쪽 게임 코드까지 손대야 했습니다. 자주 바뀌는 것은 "입력 조합"이고, 안 바뀌어야 하는 것은 "아바타가 받는 입력"이라고 정리했습니다.

01AI에게 맡긴 것
  • 기존 조작안 클래스 구조 조사
  • 입력 모듈과 위젯 생성 코드 초안
  • 재조립할 때 남는 이벤트 구독 점검
02내가 판단한 것
  • 조작안 클래스를 없애고 "프로필 데이터 + 모듈 조립"으로 바꾸는 방향
  • 아바타가 아는 범위를 입력 인터페이스 하나로 제한
  • 차지 진행 상태를 모듈 밖에 두기
03결과
  • 기존 조작안 4종을 클래스 분기 없이 프로필 조합으로 표현합니다. 기존 위젯 조합으로 되는 새 조작안은 데이터만 바꿔 추가합니다.
  • 플레이 중 조작안을 바꿔도 쌓아 둔 차지가 사라지지 않고, 일시정지 후 남은 조이스틱 입력도 초기화합니다.

배운 점. AI에게 맡기기 전에 경계를 먼저 정하면, 초안이 그 경계 안에서 나와 고칠 일이 줄었습니다.

Slime Busterscase-02 · 구조화 · 직무 경계

> Q. "서브는 관통, 랠리는 바운스" 같은 요구를 케이스 코드 없이 받으려면?

아이템과 슬라임이 함께 쓰는 스킬, 기획자가 그리는 범위

기획은 컨셉과 요구를 주고, 비슷한 효과가 아이템과 슬라임에 따로 붙을 예정이었습니다. 스킬 범위와 발동 타이밍은 밸런스 조정 때마다 바뀌었습니다. 요구가 올 때마다 케이스를 코드로 박으면 같은 로직이 계속 늘어납니다.

01AI에게 맡긴 것
  • 효과별 스킬 구현
  • 인스펙터에 그리드를 그리는 편집기 초안
  • 기획자용 사용법 문서 초안
02내가 판단한 것
  • 아이템과 슬라임이 같은 스킬 자산을 참조하는 공용 구조로 일반화
  • 발동형과 지속형으로 역할 분리
  • 범위·그룹별 발동 시각·효과음을 데이터로 뺄 범위
03결과
  • 기획자가 인스펙터에서 셀을 눌러 범위와 발동 순서, 효과음을 바로 조정합니다.
  • "관통/바운스" 요구는 차지 스킬에 효과를 붙이는 방식으로 풀어, 폭발·속도 같은 효과도 같은 틀에 추가합니다.
  • 새 종류의 행동은 여전히 코드가 필요하다는 한계도 문서에 함께 적었습니다.

배운 점. 프로그래머의 일이 기능 구현에서 끝나지 않고, 기획자가 직접 조정할 수 있는 지점을 만드는 데까지 간다는 걸 이 작업에서 정리했습니다.

Slime Busterscase-03 · AI 리더십

> Q. 비개발자가 설명 없이 슬라임 하나를 끝까지 만들 수 있을까?

콘텐츠 관계를 그래프로 편집하는 에디터 툴

슬라임, 페이즈, 스킬, 이동 패턴, 아이템, 스테이지가 여러 데이터 에셋의 참조로 이어져 있었습니다. 슬라임 하나를 만들려면 에셋 여러 개를 열고 손으로 연결해야 했고, 빠진 연결은 플레이해 봐야 드러났습니다.

01AI에게 맡긴 것
  • 노드 그래프 편집 화면 구현
  • 그래프 변경과 실제 데이터의 양방향 동기화
  • 드래그 앤 드롭 할당, 폴더 라이브러리
02내가 판단한 것
  • "툴 하나 안에서 슬라임 설정이 끝난다"는 목표
  • UX 우선순위를 정하고 제안마다 이 기준으로 선택
  • 매 단계 직접 써 보고 불편한 점 지정
03결과
  • 작성 탭 하나에서 스탯, 페이즈, 스킬, 이동 패턴까지 연결합니다. 스테이지·풀·아이템도 탭으로 묶었습니다.
  • 기존 데이터 구조를 그대로 두고 그 위에 편집 화면을 얹어, 런타임 코드는 건드리지 않았습니다.

배운 점. 기준을 문장으로 박아 두니 AI가 여러 안을 내도 고르는 시간이 짧아졌습니다. 기준이 없을 때는 그럴듯한 제안을 따라가게 됩니다.

Slime Busterscase-04 · 학습 실행력

> Q. 저사양 기기에서 광고를 본 뒤 게임이 꼬인다. 어디서부터 봤나?

광고 콜백과 기기 메모리, 측정부터 붙이기

광고 SDK 콜백, 앱 포커스 복귀, OS 저메모리 알림이 서로 다른 시점에 들어왔습니다. 그래서 입력 잠금, 보상 지급, 다음 광고 준비가 꼬였습니다. 원인 후보가 많아서, 추측으로 고치기 전에 무엇이 메모리를 쓰는지부터 보기로 했습니다.

01AI에게 맡긴 것
  • 콜백과 생명주기 이벤트의 순서 정리
  • 광고 네트워크별 메모리 계측 코드
  • 요청 버전으로 늦게 온 콜백을 구분하는 초안
02내가 판단한 것
  • 실기기 측정값을 보고 차단 기준을 정하고 조정
  • 효과가 없거나 부작용이 있던 방식은 되돌림
  • "광고 표시 중에는 해제하지 않는다" 원칙
03결과
  • 광고 표시 중 저메모리가 오면 닫힌 뒤에 정리하고, 메모리가 안정된 뒤 다시 준비합니다.
  • 이전 요청의 늦은 콜백이 새 광고 흐름을 건드리지 않습니다.
  • 광고를 끝까지 보지 않았거나 볼 수 없는 경우를 나눠, 상황별 안내를 띄웁니다.

배운 점. 처음 다루는 영역에서는 AI의 설명보다 측정값이 먼저였습니다. 계측을 먼저 붙이고 기준을 옮겨 가는 순서를 이때 익혔습니다.

Slime Busterscase-05 · 학습 실행력

> Q. 프레임이 흔들리고 슬라임이 겹친다. 원인을 어떻게 쪼갰나?

할당 지점은 하나씩, 겹침은 순서 문제로

그리드 이동 틱마다 임시 컬렉션, 람다, 이동 모션 객체가 새로 만들어졌습니다. 또 이동 속도가 다른 슬라임이 한 칸에 쌓이면 위치가 겹쳤습니다. 겹침은 속도 자체가 아니라, 같은 틱 안에서 이동 순서에 따라 스택 구성이 바뀌는 것이 원인이었습니다.

01AI에게 맡긴 것
  • 반복 경로의 할당 지점 후보 찾기
  • 버퍼와 캐시 재사용 코드
02내가 판단한 것
  • 할당 지점을 종류별로 나눠 하나씩 제거하고 각각 따로 커밋
  • 겹침의 원인이 틱 안의 순서라는 점 확인
  • 스택 정리를 틱 끝으로 미루는 처리 순서
03결과
  • 그리드 반복 컬렉션, 애니메이션 람다, 모션 객체, 슬라임 생성 경로의 임시 할당을 지점별로 없앴습니다.
  • 스택에 합류한 빠른 슬라임도 정해진 칸수만큼 이동합니다.

배운 점. 한 번에 고치면 무엇이 효과였는지 알 수 없습니다. 원인 하나에 커밋 하나로 나눠 두면, 되돌릴 때도 그 하나만 되돌리면 됩니다.

> Q. 에셋 번들을 매번 다시 받는다. 원인을 어떻게 찾았나?

AI와의 첫 작업, 실측으로 시작하기

번들 238개(Android 약 2.2GB)를 인트로에서 전부 받고, 에디터에서는 실행할 때마다 다시 받았습니다. 그때까지 동작한 이유가 "다 미리 받아 두기 때문"인지부터 확인해야 했습니다.

01AI에게 맡긴 것
  • 매니페스트와 캐시 폴더 실측
  • 번들 의존 관계를 뽑아 주는 에디터 도구
  • 요청 단위 로드 코드 초안
02내가 판단한 것
  • 원인을 정하기 전에 실측부터 하라는 지시
  • 공용 네트워크 계층을 건드리지 않는 안 선택, 계층을 바꾸는 안은 거절
  • 전투만 먼저 지연 다운로드로 바꾸는 범위
03결과
  • 런타임 의존성 처리 코드가 없었고, 15MB 번들 하나가 101MB를 끌고 오는 의존 오염과 순환 참조가 있었습니다.
  • 캐시가 6.79GB로 부풀어 한도를 넘으면 지워지고, 다시 받는 루프를 확인했습니다.
  • 요청 단위 로드와 전투 진입 시 지연 다운로드까지 동작을 확인했습니다.

배운 점. 작업 뒤 30분 회고로 "단정 전에 증거", "실험 지시는 최소한으로", "데이터 구조는 최소형으로" 체크리스트를 만들었습니다. 이후 모든 작업 규칙의 출발점입니다.

> Q. AI가 코드 한 곳만 보고 원인을 단정하면 어떻게 하나?

관측과 해석이 어긋나면 해석부터 의심하기

로비 연출 개편 중이었습니다. 일부 화면에서는 연출이 안 나오고, 연속으로 보상을 받으면 앞 구간 경험치 연출이 사라졌습니다. 다이얼로그를 다녀오면 UI가 잠기는 문제도 있었습니다.

01AI에게 맡긴 것
  • 호출 흐름을 끝까지 추적
  • 임시 스택 로그를 넣어 경로 확인
  • 처방 코드 초안
02내가 판단한 것
  • 재현 조건 확인과 기획 의도 대조
  • AI의 단정 세 번 중 하나는 제 관측이 맞았고, 원인은 테이블 데이터였음
  • 기획 의도를 결함으로 읽은 수정 두 번을 되돌리고 메모리에 고정
03결과
  • 서버 값과 화면에 보여 준 값을 나눠, 연출이 보여 준 만큼만 반영합니다.
  • 통화 판정과 표현을 분리하고, 같은 연출이 두 번 예약되어 대기열이 잠기던 문제를 고쳤습니다.

배운 점. 그 뒤로는 관측과 해석이 어긋나면 해석을 먼저 의심하고, 수치 문제는 테이블까지 보게 했습니다.

> Q. 큰 기획서를 받았을 때 무엇부터 했나?

코드보다 상태표와 질문을 먼저

별도 팝업이던 스킬 편집을 캐릭터 상세 화면의 탭 안으로 옮기는 기획서(17장)였습니다. 잠금 스킬 표시, 탭을 벗어나기 전 저장 확인, 칸형 코스트 게이지, 강화 전후 표시 등 요구가 많았습니다.

01AI에게 맡긴 것
  • 기획서와 현재 코드를 대조한 상태표
  • 합의한 조각 단위의 코드 초안
  • 화면 경로 · 동작 · 기대 결과로 된 테스트 목록
02내가 판단한 것
  • 일감 A~G로 나누고 기획 확인 질문 7개를 착수 전에 전달
  • 앞서 만든 파워칩 화면의 "이탈 전 저장" 흐름을 재사용
  • 실기기 검수와 커밋 단위 확정
03결과
  • 7일 동안 37커밋으로 탭 안 편집을 완성했습니다.
  • 검수 흐름이 이때 굳어졌습니다. 테스트 목록을 받고, 저는 실패만 짚고, 원인별로 분류해 고친 뒤, 수정은 원래 커밋에 합쳐 이력을 정리합니다.

배운 점. 질문을 먼저 보내면 구현 중간에 기획이 바뀌는 일이 줄었습니다. AI가 빨리 쓰는 만큼, 잘못된 방향으로도 빨리 가기 때문입니다.

> Q. AI와 일하면서 같은 실수가 반복되지 않게 하려면?

실패 18건을 패턴 7개로

세션이 바뀌면 AI는 지난 지적을 잊습니다. 그래서 같은 종류의 실수가 작업마다 다시 나왔습니다. 하나하나 고치는 것으로는 끝나지 않는 문제였습니다.

01AI에게 맡긴 것
  • 실패 사례 기록
  • 원인별로 기존 패턴에 분류, 맞는 게 없을 때만 새 패턴
  • 작업 끝에 패턴 대조 결과 보고
02내가 판단한 것
  • "이게 실패다"를 지정
  • 패턴과 막는 행동의 기준
  • 작업 시작 때 해당 패턴을 읽고, 바뀌면 다른 세션에도 바로 전파하는 규칙
03패턴 일부
패턴언제막는 행동
P1명시된 것을 내 판단으로 바꿈기획서 예시 이미지까지 위치·색·개수를 목록으로 만들고, 끝나면 대조
P2값을 덮어쓰는 다른 주체를 놓침애니메이터, 레이아웃 그룹처럼 값을 덮어쓰는 쪽부터 확인
P4유리한 조건 하나로만 검증실제 해상도와 실제 개수로 확인하고, 못 본 것은 "미확인"으로 보고

배운 점. 컨벤션처럼 꼭 지켜야 하는 것은 부탁이 아니라 규칙 파일로 고정했습니다. 다음 세션은 그 파일을 읽고 시작합니다.
