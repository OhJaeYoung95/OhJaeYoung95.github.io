SBcase-01구조화

입력은 클래스 대신 조립으로

문제조작 방식이 계속 바뀌어도 게임 코드는 그대로 둘 수 있을까?

전조작안마다 클래스가 따로 있어, 버튼 배치만 바꿔도 캐릭터 쪽 게임 코드까지 고쳐야 했음
후조작안은 설정 데이터와 입력 부품의 조합. 있는 부품으로 되는 조작안은 데이터만 추가

기획 단계에서 조작안이 여러 번 바뀌고 종류도 늘었습니다. 그런데 조작안마다 클래스를 두는 구조라, 버튼 배치 하나만 바꿔도 아바타 쪽 게임 코드까지 고쳐야 했습니다. 그래서 자주 바뀌는 쪽은 "입력 조합", 바뀌면 안 되는 쪽은 "아바타가 받는 입력"으로 먼저 나눴습니다.

AIAI가 한 일
  • 기존 조작안 클래스 구조 조사
  • 입력 모듈과 위젯 생성 코드 초안
  • 재조립할 때 남는 이벤트 구독 점검
나제가 검토하고 정한 것
  • 결정조작안 클래스를 없애고 "프로필 데이터 + 모듈 조립"으로 바꾸는 방향
  • 결정아바타가 아는 범위를 입력 인터페이스 하나로 제한
  • 결정힘을 모으는 공격(차지)의 진행 상태는 모듈 밖에 두기
결과
  • 기존 조작안 4종을 클래스 분기 없이 프로필 조합으로 표현합니다. 있는 위젯을 조합해 만들 수 있는 조작안이라면 데이터만 추가하면 됩니다.
  • 플레이 중 조작안을 바꿔도 쌓아 둔 차지가 사라지지 않고, 일시정지 뒤에 남아 있던 조이스틱 입력도 초기화됩니다.

돌아보며. 경계를 정한 다음 AI에게 맡기니 초안이 그 경계 안에서 나왔고, 고칠 일도 줄었습니다.

SBcase-02구조화 · 직무 경계

아이템과 슬라임이 함께 쓰는 스킬, 기획자가 그리는 범위

문제"서브는 관통, 랠리는 바운스" 같은 요구를 케이스 코드 없이 받으려면?

전기획 요구가 올 때마다 그 경우만 처리하는 코드를 새로 추가
후아이템과 슬라임이 같은 스킬을 함께 쓰고, 범위·발동 시각·효과음은 데이터로 조정

기획에서는 컨셉과 요구를 받았고, 비슷한 효과가 아이템과 슬라임에 따로 붙을 예정이었습니다. 스킬 범위와 발동 타이밍도 밸런스를 조정할 때마다 바뀌었습니다. 요구가 올 때마다 케이스를 코드로 넣으면 같은 로직이 계속 늘어날 상황이었습니다.

AIAI가 한 일
  • 효과별 스킬 구현
  • 인스펙터에 그리드를 그리는 편집기 초안
  • 기획자용 사용법 문서 초안
나제가 검토하고 정한 것
  • 결정아이템과 슬라임이 같은 스킬 자산을 참조하는 공용 구조로 일반화
  • 결정발동형과 지속형으로 역할 분리
  • 결정데이터로 뺄 항목: 범위, 그룹별 발동 시각, 효과음
결과
  • 기획자가 인스펙터에서 셀을 눌러 범위와 발동 순서, 효과음을 바로 조정합니다.
  • "관통/바운스" 요구는 차지 스킬에 효과를 붙이는 방식으로 풀었고, 폭발·속도 같은 효과도 같은 틀에 붙여 추가합니다.
  • 새 종류의 행동은 여전히 코드가 필요하다는 한계도 문서에 함께 적었습니다.

돌아보며. 기획자가 직접 만질 수 있는 지점까지 만들어 두는 것도 프로그래머의 일이라고 이 작업에서 정리했습니다.

SBcase-03AI 리더십

콘텐츠 관계를 그래프로 편집하는 에디터 툴

문제비개발자가 설명 없이 슬라임 하나를 끝까지 만들 수 있을까?

전슬라임 하나를 만들려면 데이터 파일 여러 개를 열어 손으로 연결
후편집 화면 하나에서 능력치, 단계, 스킬, 이동 패턴까지 연결

슬라임, 페이즈, 스킬, 이동 패턴, 아이템, 스테이지가 여러 데이터 에셋의 참조로 이어져 있었습니다. 슬라임 하나를 만들려면 에셋 여러 개를 열고 손으로 연결해야 했고, 빠진 연결은 플레이해 봐야 드러났습니다.

AIAI가 한 일
  • 노드 그래프 편집 화면 구현
  • 그래프 변경과 실제 데이터의 양방향 동기화
  • 드래그 앤 드롭 할당, 폴더 라이브러리
나제가 검토하고 정한 것
  • 결정"툴 하나 안에서 슬라임 설정이 끝난다"는 목표
  • 결정UX 우선순위를 정하고 제안마다 이 기준으로 선택
  • 결정단계마다 직접 써 보고 불편한 점 짚기
결과
  • 작성 탭 하나에서 스탯, 페이즈, 스킬, 이동 패턴까지 연결합니다. 스테이지·풀·아이템도 탭으로 묶었습니다.
  • 기존 데이터 구조를 그대로 두고 그 위에 편집 화면을 얹어, 런타임 코드는 건드리지 않았습니다.

돌아보며. 고르는 기준을 문장으로 적어 두니 AI가 안을 여러 개 내도 금방 고를 수 있었습니다. 기준이 없을 때는 그럴듯한 제안을 그대로 따라가기 쉬웠습니다.

SBcase-04학습 실행력

광고 콜백과 기기 메모리, 측정부터

문제광고를 보고 나면 게임이 꼬이는데 원인 후보가 너무 많다면, 무엇부터 봐야 할까?

전광고 종료 알림, 앱 복귀, 메모리 부족 알림이 엇갈려 입력 잠금·보상·다음 광고 준비가 꼬임
후광고 중 메모리 부족은 광고가 닫힌 뒤 처리하고, 늦게 도착한 이전 알림은 무시

저사양 기기에서 광고 SDK 콜백, 앱 포커스 복귀, OS 저메모리 알림이 제각각 다른 시점에 들어오면서 입력 잠금, 보상 지급, 다음 광고 준비가 서로 꼬였습니다. 원인 후보가 많아서, 추측으로 고치기 전에 무엇이 메모리를 쓰는지부터 측정하기로 했습니다.

AIAI가 한 일
  • 콜백과 생명주기 이벤트의 순서 정리
  • 광고 네트워크별 메모리 계측 코드
  • 요청 버전으로 늦게 온 콜백을 구분하는 초안
나제가 검토하고 정한 것
  • 결정실기기 측정값으로 차단 기준을 정하고 조정
  • 거절효과가 없거나 부작용이 있던 방식은 되돌리기
  • 결정"광고 표시 중에는 해제하지 않는다" 원칙
결과
  • 광고가 떠 있을 때 저메모리 알림이 오면 광고가 닫힌 뒤에 정리하고, 메모리가 안정되면 다음 광고를 다시 준비합니다.
  • 이전 요청에서 늦게 도착한 콜백이 새 광고 흐름을 건드리지 않습니다.
  • 광고를 끝까지 보지 않은 경우와 광고를 볼 수 없는 경우를 나눠, 각각에 맞는 안내를 띄웁니다.

돌아보며. 처음 다루는 영역이라 AI의 설명보다 측정값을 먼저 믿었습니다. 계측부터 붙이고, 측정값을 보며 기준을 조정해 가는 순서를 이때 익혔습니다.

SBcase-05학습 실행력

할당 지점은 하나씩, 겹침은 순서 문제로

문제프레임이 흔들리고 슬라임이 겹친다면, 원인을 어떻게 나눠 볼까?

전이동할 때마다 임시 객체가 새로 생기고, 한 칸에 모인 슬라임 위치가 겹침
후임시 객체를 생기는 곳마다 없애고, 겹침 정리는 이동이 모두 끝난 뒤에 처리

문제는 두 가지였습니다. 그리드 이동 틱마다 임시 컬렉션, 람다, 이동 모션 객체가 새로 만들어졌고, 이동 속도가 다른 슬라임이 한 칸에 쌓이면 위치가 겹쳤습니다. 겹침의 원인은 속도 차이보다, 같은 틱 안의 이동 순서에 따라 한 칸에 모이는 슬라임 묶음이 달라지는 데 있었습니다.

AIAI가 한 일
  • 반복 경로의 할당 지점 후보 찾기
  • 버퍼와 캐시 재사용 코드
나제가 검토하고 정한 것
  • 결정할당 지점을 종류별로 나눠 하나씩 제거하고 각각 따로 커밋
  • 결정겹침 원인이 틱 안의 이동 순서임을 확인
  • 결정칸마다 모인 슬라임 정리를 틱 끝으로 미루는 처리 순서
결과

  • 다른 슬라임 위에 합류한 빠른 슬라임도 정해진 칸 수만큼 이동합니다.

돌아보며. 한꺼번에 고치면 어떤 수정이 효과였는지 알 수 없습니다. 원인 하나에 커밋 하나씩 나눠 두면 되돌릴 때도 그 커밋만 되돌리면 됩니다.

TA에서 AI와 한 첫 작업, 실측부터

문제에셋 번들을 매번 다시 받는 이유를 추측 없이 찾으려면?

전게임 시작 때 리소스 묶음을 전부 받고, 에디터에서는 실행할 때마다 다시 받음
후필요할 때 필요한 것만 받고, 전투 리소스는 전투에 들어갈 때 받음

수백 개, 수 GB 규모의 번들을 인트로에서 전부 받고 있었고, 에디터에서는 실행할 때마다 다시 받았습니다. 요청 단위로 바꾸려면, 지금까지 문제없이 돌아간 이유가 "전부 미리 받아 두기 때문"인지부터 확인해야 했습니다.

AIAI가 한 일
  • 매니페스트와 캐시 폴더 실측
  • 번들 의존 관계를 뽑아 주는 에디터 도구
  • 요청 단위 로드 코드 초안
나제가 검토하고 정한 것
  • 지시원인을 정하기 전에 실측부터 하도록 지시
  • 거절공용 네트워크 계층을 건드리지 않는 안을 고르고, 계층을 바꾸는 안은 거절
  • 결정지연 다운로드는 전투부터 적용하는 범위
결과
  • 실측해 보니 런타임에서 의존성을 처리하는 코드가 없었고, 작은 번들 하나가 몇 배 크기를 끌고 오는 의존 오염과 순환 참조도 있었습니다.
  • 캐시가 수 GB까지 불어 한도를 넘으면 지워지고 다시 받는 루프도 확인했습니다.
  • 이후 요청 단위 로드와 전투 진입 시 지연 다운로드까지 만들어 동작을 확인했습니다.

돌아보며. 작업을 마치고 30분 동안 회고하며 "단정 전에 증거", "실험 지시는 최소한으로", "데이터 구조는 최소형으로" 체크리스트를 만들었습니다. 이후 작업 규칙의 출발점이 됐습니다.

문제AI가 코드 한 곳만 보고 원인을 단정하면, 어디서 멈춰야 할까?

전AI가 코드 한 곳만 보고 원인을 단정
후제가 본 현상과 어긋나면 다시 확인. 실제 원인은 테이블 데이터였음

로비 연출을 개편하던 중이었습니다. 일부 화면에서는 연출이 나오지 않았고, 보상을 연속으로 받으면 앞 구간의 경험치 연출이 사라졌습니다. 다이얼로그를 열었다 돌아오면 UI가 잠기는 문제도 있었습니다. AI가 원인을 추적하는 과정에서 코드 한 곳만 보고 단정한 경우가 세 번 있었습니다.

AIAI가 한 일
  • 호출 흐름을 끝까지 추적
  • 임시 스택 로그를 넣어 경로 확인
  • 처방 코드 초안
나제가 검토하고 정한 것
  • 결정재현 조건 확인과 기획 의도 대조
  • 지시제 관측과 어긋난 단정의 재확인 지시 (실제 원인은 테이블 데이터)
  • 거절AI가 기획 의도를 결함으로 보고 고친 것 두 번을 되돌리고, 의도를 메모리에 고정
결과
  • 서버 값과 화면에 보여 준 값을 따로 두고, 연출로 보여 준 만큼만 화면에 반영합니다.
  • 특정 연출(전화가 걸려 오는 이벤트)을 띄울지 정하는 코드와 화면에 보여 주는 코드를 나누고, 같은 연출이 두 번 예약되어 대기열이 잠기던 문제를 고쳤습니다.

돌아보며. 그 뒤로 관측과 해석이 어긋나면 해석부터 의심하고, 수치 문제는 테이블까지 확인하게 했습니다.

나제가 검토하고 정한 것
  • 결정일감 7개로 나누고 기획 확인 질문 7개를 착수 전에 전달
